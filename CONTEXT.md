# PolySIEM domain context

## Inventory and evidence

- **Asset** — A durable thing PolySIEM documents, such as a hypervisor, VM, container, firewall, or switch. An inventory integration owns the lifecycle of the assets it creates.
- **Configured address** — An IP address declared in an asset or interface configuration. It is direct configuration evidence, not proof that the address is currently reachable.
- **Network observation** — An address, MAC, or hostname seen by a network integration through DHCP, ARP, neighbor discovery, or a similar runtime source. Observations describe what the network saw; they do not own the matching asset.
- **Address claim** — One integration's evidence that an asset or MAC uses an IP address. Claims retain their source and may agree, complement, or conflict with other claims.
- **Resolved footprint** — The derived topology view produced by conservatively joining assets, configured addresses, and network observations. It is not itself a new source of inventory truth.

## Identity resolution

- Exact normalized MAC address is the preferred cross-integration join key for an interface.
- A MAC observation is attached to an asset only when that MAC identifies exactly one active asset interface. Ambiguous matches stay as independent network observations.
- Configured addresses are retained even when no network integration observes them. Observed addresses fill gaps and never overwrite configuration owned by another integration.
- Hostname similarity alone is insufficient to merge assets or attach addresses.

## Firewall evidence

- **Gateway policy** — Inter-network policy enforced by a router or firewall integration, such as OPNsense.
- **Workload policy** — Datacenter, security-group, or guest-local policy enforced around a hypervisor workload, such as Proxmox firewall rules.
- Gateway and workload policies are complementary layers. The access map may derive both, but must not reinterpret workload rules as gateway routing policy.

## Edge networks

- **Edge NAT Server** — A small remote Linux host that owns a public packet boundary and forwards only explicitly managed listeners toward the private lab. Its public address replaces the home WAN address at the packet layer, but it is not proof that applications, DNS, logs, or WebRTC cannot reveal other addresses.
- **Edge NAT listener interface** — The Linux interface on which published traffic arrives. It describes a traffic role, not a permanently “public” network zone.
- **Edge NAT target-path interface** — The Linux interface selected by the route toward the DNAT target. It may be the same as the listener interface when a single-NIC edge server forwards to a public residential address, or a tunnel interface such as `tailscale0` when the target is private.
- **Edge NAT Rule** — PolySIEM's desired TCP or UDP mapping on one Edge NAT Server. A saved rule is not evidence of reachability until the server confirms that revision was applied.
- **Applied edge rule** — A desired Edge NAT Rule whose managed remote firewall state has been verified. Only applied rules may contribute reachable paths to topology views.
- **Edge Networks** — A derived operational view combining Edge NAT, Tailscale, Cloudflare, firewall, and observed routing evidence. It does not own or silently merge the underlying providers' source data.
- **Connector** — A far end of a WireGuard tunnel that PolySIEM records: an agent, an OPNsense box, or another peer. Every kind dials out to the edge and holds the tunnel open, so nothing at home needs a public IP or an inbound port. Kinds differ only in how much of the far side PolySIEM manages. A connector is a **standalone** concept, not part of one edge box: it is installed once, its name is unique instance-wide, and it belongs to no Edge NAT Server.
- **Connector link** — The join between one connector and one Edge NAT Server. It carries the tunnel address allocated for that pairing, an enabled flag, and the last handshake seen there. Links are what make a connector reusable: one installed connector serves every edge box it is linked to, and an edge box may route through any connector linked to it. Removing a link is refused while enabled connector-mode rules on that edge still target that connector; the refusal names them, and the operator retargets or removes those rules first.
- **Per-edge tunnel address** — Each edge box has its own tunnel subnet, so the address a connector answers on is a property of the link, not of the connector. A connector serving two edges holds a different tunnel IP on each, and both are allocated by PolySIEM. An address quoted without naming the edge it belongs to is ambiguous.
- **One interface, many peers** — A connector agent runs a single WireGuard interface carrying one peer per linked edge and one address per link. PolySIEM never creates a network device per edge box. Because two edges may publish the same public port to the same connector, every last-hop rule is scoped by the destination address of the edge that published it.
- **Connector kind** — What sits at the far end: `agent` (PolySIEM's own agent on a Linux host — token, managed SSH key, pushed rules, and it performs the final hop itself), `opnsense` (an OPNsense firewall the operator configures by hand), or `peer` (any other WireGuard endpoint, behaviourally identical to `opnsense`). The kind is chosen when the connector is added and decides which management story applies, never whether the far end is a connector.
- **Manual connector** — A connector of kind `opnsense` or `peer`. PolySIEM issues it no install token, no SSH keypair, and no pushed ruleset: it is purely a WireGuard peer of the edge. OPNsense is therefore a kind of connector, not a separate manual-peer concept, and the old standalone OPNsense peer entry survives only as a read-only legacy field.
- **Paste-ready peer block** — The values a manual connector's far side needs for ONE edge box: that edge's endpoint, its public key, the AllowedIPs for the edge peer, the tunnel address allocated on that link, and the keepalive. There is one block per link, because the address and the endpoint are per edge. PolySIEM shows the block and accepts the far side's PUBLIC key back; that single key identifies the peer on every edge it is linked to, and the far side always initiates, because the edge only listens.
- **Manual connector status** — Derived from configuration, not liveness: `pending` until the far side's public key is registered, `configured` once it is, `disabled` when the operator turns it off. A manual connector never reports `connected`, because PolySIEM has no agent there to prove liveness with.
- **Connector ID** — The stable public identifier of one connector. It is quoted in install output and route configuration; it is not a credential, and it is unrelated to the one-time install token that enrolls the agent.
- **Implicit tunnel address** — The tunnel IP PolySIEM allocates when a connector is linked to an edge box. It is derived from that edge's tunnel subnet and is never entered by an operator, so it is control-plane bookkeeping rather than declared configuration.
- **Connector SSH push** — The primary connector management transport: PolySIEM opens an authenticated SSH session to the connector and runs the agent's STATUS or APPLY action directly. It is available only once an SSH endpoint, an enrolled host key, and PolySIEM's managed key all exist, and it is the authoritative source of live connector health.
- **Connector token poll** — The fallback connector management transport retained from the pull model: the agent periodically fetches its desired configuration with its own token. It is self-healing and remains the only path when PolySIEM cannot reach the connector inbound. Both transports converge on the same canonical ruleset and hash, so an applied revision means the same thing whichever path delivered it.
- **Connector SSH key custody** — PolySIEM generates and owns one SSH keypair per connector. The private half stays in PolySIEM's encrypted credentials and appears in no DTO, log, audit record, or screen; the authorized line installed on the connector is restricted to running the connector agent, so the key cannot open a shell. Revoking one connector's key does not affect any other.
- **Connector WireGuard key custody** — The connector generates its own WireGuard private key on the machine and never transmits it. PolySIEM only ever learns the public half, reported through STATUS or enrollment, and registers it as an edge peer. A management transport that carried a WireGuard private key would violate this rule regardless of direction.
- **Connector host-key enrollment** — The operator confirms a scanned SSH host-key fingerprint through the machine's own console and pins it. Afterwards every PolySIEM connection is checked against the pinned key; an unpinned or changed host key is refused rather than accepted on trust.
- **Direct route mode** — An Edge NAT Rule whose edge DNATs straight to a target the edge itself can reach. This is the original primitive and remains the default.
- **Connector route mode** — An Edge NAT Rule whose edge forwards the published port over the tunnel to a chosen connector, which then reaches the target as seen from the connector. The rule is valid only while a live link joins that rule's edge box to that connector, and the edge DNATs to the connector's address on THAT edge. Both modes coexist in one applied ruleset; a saved connector rule is not evidence of reachability until the connector has enrolled and the revision is applied.
- **Manual-connector last hop** — A connector-mode rule targeting a manual connector is applied only as far as the tunnel: the edge DNATs the published port to that peer's tunnel address on that edge, and the operator owns the hop from there to the service (an OPNsense port forward, for example). PolySIEM cannot program that side, so such a rule is evidence of the edge's intent only.
